# 门店离线收银优惠券核销失败 —— 根因定位与止损方案

> **一句话结论：核销失败的主因不是"券额度不够"，也不是"某类券/某家店/高峰压力"，而是收银机本地券状态快照已经过期——22.5% 的请求发生在快照滞后 ≥20 分钟时，它们贡献了 74.3% 的失败。把"快照新鲜度"做成核销前的门控条件，能在不改造后端的前提下拿回约 74% 的失败损失。**

| 关键数字（由 `analyze.py` 从原始数据算出） | 值 |
|---|---|
| 分析样本（清洗后） | 945 笔 |
| 总体失败率 | 101 / 945 = **10.7%** |
| 快照滞后 ≥20 分钟的请求 | 213 笔，**22.5%** |
| 这些请求的失败率 | 75 / 213 = **35.2%** |
| 快照新鲜请求的失败率 | 26 / 732 = **3.6%** |
| 风险比 RR / Pearson χ² (df=1) | **9.91** / 173.2，**p = 1.5e-39** |
| 滞后组对全部失败的贡献 | **74.3%** |
| 样本期直接损失（101 × 75 元） | **7,575 元** |

## 一、我的判断：看到了什么

> 本节回答：**数据里能看到的信号是什么，以及为什么排除了其他解释。** 根问题单独放在第二节。

### 1.1 先对表，再算指标

原始 1024 行，先做数据审计，结果不算干净：

| 问题 | 行数 | 处理 |
|---|---|---|
| 整行完全重复（`redemption_id` 也重复） | 49 | 去重，保留首条 |
| `is_success` 缺失 | 32（去重后 30） | 从对比主分析里剔除，另做敏感性检验 |
| **最终分析样本** | **945** | 剔除 79 行（7.7%） |

49 条重复是**整行完全一致**的重复（不是同一笔的多次核销），判断为导出/粘贴时的重复行，直接去重。我没有把重复行当"多笔请求"计入，否则会把失败率算偏。

### 1.2 一个差点让结论完全反向的坑：时区

- `redeem_time` 是 `+08:00`（本地时间）
- `snapshot_synced_at` 是 `Z`（UTC）

两者**直接相减会得到约 −8 小时的"负滞后"**。如果按字面直接减，所有快照都会显示"比核销时间还晚"，滞后与失败的关系会被彻底抹掉甚至反向。脚本里统一转成 UTC 再相减（`pd.to_datetime(..., utc=True)`）。

清洗后滞后范围是 0–70 分钟，**没有任何负值**（`negative_lag: 0`），说明时区处理是对的。

### 1.3 定义唯一的新指标：`lag_min`

```
lag_min = redeem_time(UTC) - snapshot_synced_at(UTC)   # 单位：分钟
```

数据里 945 笔请求对应 878 个不同的 `snapshot_synced_at` 时间点（中位复用 1 笔/时间点），说明**快照基本是随每笔交易刷新的**。所以 `lag_min` 可以直接读作：

> **这台收银机距上一次成功同步券状态，已经过去多久。**

这个读法很关键——它把一个静态的时间差，变成了一个可以实时计算、可以拿来做门控的运营指标。

---

### 1.4 核心信号：滞后分布是双峰的，中间有一条空档

按分钟看 `lag_min` 的样本量（`output/tables/lag_distribution.csv`）：

- **0–18 分钟：732 笔，密集均匀**
- **19、20、21 分钟：0 笔**
- **22–70 分钟：213 笔，稀疏但连续**

19–21 分钟**一笔都没有**。这不是随机波动能产生的形状。它说明系统里存在两种运行状态：

- **正常态**：快照同步按预期节奏刷新，滞后天然落在 20 分钟以内（同步周期 + 网络抖动）；
- **异常态**：同步已经连续错过至少一个周期，滞后跳到 22 分钟以上，并且会持续（滞后中位数 **44 分钟**，最长 **70 分钟**）。

**20 分钟不是我先验设的阈值，是数据里自己长出来的断层。**（后面的阈值扫描会再验证一次：净收益最优点正好落在这个 19–22 的空档里。）

### 1.5 断层两侧的失败率差了近 10 倍

| 分组 | 请求数 | 失败数 | 失败率 |
|---|---|---|---|
| 快照新鲜（lag < 20 min） | 732（77.5%） | 26 | **3.6%** |
| 快照陈旧（lag ≥ 20 min） | 213（22.5%） | 75 | **35.2%** |

- 风险比 **RR = 9.91**
- Pearson χ² = 173.2（df=1），**p = 1.5e-39**
- **滞后请求只占 22.5% 的量，却贡献了 74.3% 的失败**

这就是问题的形状：**不是普遍性的系统差，而是一个可以被精确定位的小口子在漏。** 这类问题最适合用"精准门控"而不是"全线加固"来解决——成本差一个数量级。

### 1.6 排除了其他四个解释

我不想把"相关"当"根因"，所以逐条验伪：

| 假设 | 检验方式 | 结论 |
|---|---|---|
| **某类券有问题** | 8 个券种各自失败率 | 8.9%–13.2%，极差仅 **4.4 个百分点**，远小于 stale/fresh 之间的 31.6 个百分点。**否** |
| **某家门店设备有问题** | 5 家门店各自失败率 | 8.1%–14.4%，差异基本是各家 stale 比例的镜像。**主因否**，但见下方例外 |
| **高峰客流把系统压垮** | 只看新鲜快照，按小时拆失败率 | 0%–5.9% 之间平坦波动，**没有随客流抬升**。高峰只是让同步更容易断，不是独立致因。**否** |
| **券额度耗尽（`remaining_quota=0`）** | 在新鲜快照内比较 | 额度=0 时失败率 17.4%（4/23）vs 额度>0 时 3.1%（22/709）。**有独立影响，但只占样本 3.5%，量级是次级** |

另外 `corr(lag_min, remaining_quota) = -0.02`、`corr(lag_min, order_amount) = 0.15`，滞后不是额度或客单价的代理变量。

**一个需要单列的门店例外：皇姑店。** 剥离 stale 之后，其他 4 家店的新鲜快照失败率均值只有 2.3%，而皇姑店仍有 **9.0%（12/133，p = 0.0002）**。

这个店值得单独说，因为**它的两个数字方向是反的**：stale 比例全 5 家最高（28.5%），总失败率却全 5 家最低（8.1%）。矛盾在分层后才解开——皇姑店的失败没有集中在 stale 里，它在快照新鲜时就已经大量失败。其他 4 家店的问题是"同步断"，皇姑店是"同步断 + 另一处独立故障"。

**教训：只看总失败率，会漏掉最该修的那家店。** 皇姑店要单独开排查单（本地缓存损坏、单机网络、客户端版本），不能靠同步策略覆盖。这是本次分析里唯一被我判定为"门店级"的异常，其余门店差异都只是同步问题的投影。

## 二、根问题是什么：不是券不够，是"本地以为券还在"

把上面的证据串成机制：

```
顾客出示券
   ↓
收银机读本地快照 remaining_quota  ── 快照是 20~70 分钟前的
   ↓
本地判断"有额度" → 发起核销
   ↓
云端按当前真实状态判定 → 券已被别处核销 / 活动已变更 / 额度已尽 → 拒绝
   ↓
❌ 核销失败，收银台卡住，队伍堆积，客诉
```

**根问题：总部→门店的券状态同步链路不可靠，且收银端没有任何"我的数据可能过期"的自我感知。** 系统在快照陈旧时仍然用陈旧数据做"能核销"的判断，把不一致推迟到服务端才暴露——而暴露的时机正好是顾客站在收银台前的那几秒。

反过来看一个有意思的现象：`remaining_quota = 0` 时核销成功率仍有 **75.8%**。说明收银端并没有把本地 0 额度当硬拦截（否则不可能成功），**它的问题是不敢/不会在快照可疑时主动去云端要一次真相**。这恰好是门控方案能生效的前提。

> 需要说明的边界：数据里没有云端侧状态、没有设备 ID、没有同步任务的日志，所以"云端拒绝了什么"这一步是**推断**，不是直接观测。我观测到的是确定的：滞后与失败的强关联、以及断层的位置。机制解释与此完全自洽，但严格的因果证明需要同步任务日志或服务端拒绝码——**这是本分析最大的盲区**，见第五节。

## 三、做了什么：三层方案

我按"能多快落地"排序，而不是按"多彻底"排序。

### P0｜今天就能上：核销前的新鲜度门控

在收银端核销流程前插入一个判断，**只对可疑请求付出联网代价**：

```python
# 伪代码：收银端核销前置检查
lag = now_utc() - coupon.snapshot_synced_at

if lag > 20 * 60 or coupon.remaining_quota == 0:
    state = cloud.verify(coupon)      # 联网强制校验，成本 10 元
    if not state.redeemable:
        # 提前给出"这张券当前不可用"的明确提示 + 推荐可用券
        return HUMAN_READABLE_REJECT
    coupon = state                     # 用真实状态继续核销
# 否则走原离线快照路径，零成本
```

要点：
- **只对 25.0% 的请求（236/945：滞后 ≥20 分钟 213 笔 + 快照新鲜但额度为 0 的 23 笔）付费**，其余 75% 的核销仍然完全离线、零延迟。
- 失败从"收银台卡住"提前变成"收银前提示"，同样的失败，客诉成本差很多。
- 阈值 20 分钟来自数据断层（见 4.2 的扫描），不是我拍的。

### P1｜治本：把同步链路做可靠

门控只是止损，真正的解法是让滞后不再发生：

1. **同步心跳与自愈**：收银端记录"上次成功同步时间"，超过 N 分钟未成功就主动重试 / 切换备用地址；连续失败告警到门店运维。
2. **同步周期对齐**：当前正常态上限约 18–20 分钟，应把目标周期压到 10 分钟以内并留抖动余量，让 20 分钟这条线变成"几乎不可能越过的红线"。
3. **状态变更主动推送**：券额度变更、活动下线这类事件，用推送替代轮询，从根上消掉"不知道券已经没了"的窗口。
4. **收银端显示数据新鲜度**：UI 上标一行"券状态更新于 X 分钟前"，让收银员在异常时自己知道该刷新。

### P2｜体验兜底：离线记账 + 事后冲正

即使门控到位，仍有约 3.6% 的基础失败率（网络抖动、并发核销冲突）。这部分不该让顾客承担：

- 核销失败时**不要让交易整体失败**：按离线记账放行，事后异步冲正/补扣。
- 或提供"本单改用手动折扣/下次补偿券"，把技术失败转成可接受的商业处理。

### 并行的门店专项

按 1.6 的结论，**皇姑店单独开一张排查单**（设备网络、本地缓存完整性、客户端版本），它的 9.0% 残差不在主策略覆盖范围内。

## 四、怎么证明有用

所有数字都由 `analyze.py` 计算并可复现，明细表落在 `output/tables/`。

### 4.1 策略对比（945 笔逐笔测算）

口径：失败 75 元/次，联网校验 10 元/次。

**保守口径**——假设联网校验后失败率不是归零，而是降到"快照新鲜"的基线 3.6%（因为校验本身也可能超时/失败）：

| 策略 | 触发校验 | 校验成本 | 挽回失败 | 净收益 |
|---|---|---|---|---|
| A. 全部强制联网校验 | 945 | 9,450 | 67.4 | **−4,392 元（亏）** |
| B. 仅额度=0 时校验 | 33 | 330 | 6.8 | +182 元 |
| **C. 仅滞后 ≥20 min 时校验** | **213** | **2,130** | **67.4** | **+2,928 元** |
| D. 滞后 ≥20 min **或** 额度=0 | 236 | 2,360 | 70.6 | +2,936 元 |
| E. 根因修复（滞后压到 20 min 内） | 0 | 0 | 67.4 | **+5,058 元** |

**乐观口径**（校验后失败率归零）：C 为 +3,495 元、D 为 +3,565 元；**全量校验 A 仍然是亏的（−1,875 元）**。

这张表是整个方案最有说服力的地方：

- **全量加固是错的**：给每一笔核销都加联网校验，保守口径下成本 9,450 元 vs 挽回 5,058 元，净亏 4,392 元。盲目"提高校验强度"会把钱烧在 77.5% 本来就没问题的请求上。
- **精准门控是对的**：只对 25% 的可疑请求付费，净赚 2,928 元（保守）/ 3,495 元（乐观）。
- **根因修复收益最高**：零边际成本拿回 5,058 元，是门控（保守口径 2,928 元）的 1.7 倍——所以 P0 只是止血，P1 才是必须做的。

### 4.2 20 分钟这个阈值是数据选出来的，不是我定的

对 t = 1…50 逐分钟扫描"只对 lag ≥ t 的请求强制校验"的净收益（`output/tables/threshold_scan.csv`，保守口径）：

| t（分钟） | 触发校验 | 挽回失败 | 净收益 |
|---|---|---|---|
| 12 | 477 | 64.1 | +34 |
| 15 | 343 | 64.8 | +1,431 |
| 18 | 250 | 66.1 | +2,459 |
| **19–22** | **213** | **67.4** | **+2,928（最优平台）** |
| 25 | 198 | 64.0 | +2,818 |
| 30 | 174 | 54.8 | +2,372 |

最优点是一个**平台（19–22 分钟）**，而它恰好落在 1.4 里那条"零观测空档"上。两个独立视角（分布断层、收益扫描）指向同一个位置——这就是我把 20 分钟写进 P0 规则的原因。

阈值再往下调（t=12）会把大量正常请求也拉去联网，净收益被校验成本吃掉；到 **t=11 就转亏（−245 元）**。**这也解释了为什么"多校验一点更保险"的直觉在本题里是错的。**

### 4.3 结论对数据质量问题不敏感

把 30 笔缺失的 `is_success` 分别当成全失败 / 全成功：

| 缺失处理 | stale 失败率 | fresh 失败率 | RR |
|---|---|---|---|
| 全当失败 | 37.8% | 6.2% | 6.06 |
| 全当成功 | 33.8% | 3.5% | 9.78 |

两种极端下 RR 都在 6–10 之间，**结论不翻转**。缺失行本身的 stale 比例是 30.0%（全样本 22.5%），与滞后基本无关，可按随机缺失处理。

### 4.4 规模化口径（线性外推，**非实测**）

样本跨 7 天 × 5 店。按每 1000 笔核销折算：

- 失败约 **107 笔**，直接损失约 **8,016 元**
- 需触发联网校验约 **225 次**，成本 2,250 元

> ⚠️ 这一段是**按样本线性外推**的假设值，用于量级沟通，**不作为结论依据**。真实规模需要门店数、日均核销量和同步故障率才能算。

## 五、我不知道的部分

诚实列出来，这些都会影响方案的最终形态：

1. **机制是推断，不是直接观测。** 数据里没有云端真实券状态、没有服务端拒绝码，我无法直接证明"失败是因为云端拒绝"。如果部分失败其实是收银端网络超时造成的，P0 的联网校验收益会打折扣（校验同样要联网）。
2. **没有设备维度。** 无法区分"某台收银机的同步坏了"还是"整店的网络坏了"，P1 的自愈策略粒度只能到门店。
3. **样本只有 7 天、5 店、945 笔**，且促销期与平销期的券结构可能不同；外推到全年需谨慎。
4. **门控的隐性成本没算进去**：联网校验会带来 0.3–2 秒的额外等待，高峰期可能反而加剧排队。**建议小流量灰度，实测校验耗时后再全量。**
5. **失败 75 元的损失口径偏财务**，不含客诉处理、复购流失等软性损失；如果计入，P0/P1 的优先级只会更高不会更低。
6. 皇姑店的 9.0% 残差具体成因未定位，需要设备日志。
